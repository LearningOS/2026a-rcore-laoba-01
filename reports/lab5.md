## 一、功能总结

在 ch8 内核（已有线程、mutex / semaphore / condvar、FIFO 调度）的基础上，实现了 `sys_enable_deadlock_detect`（ID 469）与死锁检测。

- **开关**：`ProcessControlBlockInner` 增加 `deadlock_detect: bool`；`sys_enable_deadlock_detect` 按参数设置并返回 0；`fork` 时子进程继承父进程的开关。
- **资源账本**（进程级）：`mutex_owner` 记录每个 mutex 的持有 tid，`sem_total` 记录每个信号量的初始容量，`sem_alloc[tid][sem]` 记录每个线程持有的信号量数量，`sem_request[tid]` 记录线程正在等待的信号量；另保留 `mutex_request` 供后续扩展。
- **mutex**：`sys_mutex_lock` 在真正加锁前检查“当前线程是否已经持有该 mutex”，是则直接返回 `-0xdead`，不进入阻塞。
- **semaphore**：`sys_semaphore_down` 先由账本算出剩余量；剩余量为 0 时登记本次请求，再用银行家算法的安全序列判断：存在安全序列则照常阻塞，不存在则返回 `-0xdead` 并且**不调用 `down`**。`sys_semaphore_create` / `sys_semaphore_up` 同步账本。
- **安全序列判定** `deadlock_safe()`：`work = 各信号量总量 − 所有线程已持有量`；反复把“没有在等信号量，或等待的那个还有余量”的线程标记为可完成，并把它持有的资源加回 `work`；所有线程都能完成则安全，否则判定为死锁。
- **移植**：把 ch4 的 `sys_get_time` 搬回 ch8。ch8 模板里它仍是返回 `-1` 的桩，而 `user_lib::sleep()` 是用户态忙等（`while get_time() < start + ms { sys_yield(); }`），不修的话测例主线程永远离不开 `sleep`。

验证结果：

- `ch8_deadlock_mutex1`：重复加锁同一个 blocking mutex，第二次返回 `-0xdead`，输出 `deadlock test mutex 1 OK!`。
- `ch8_deadlock_sem1`：三个线程形成循环等待，tid2 请求 sem3 时判定不安全并返回 `-0xdead`，输出 `deadlock test semaphore 1 OK!`。
- `ch8_deadlock_sem2`：资源紧张但存在安全序列，未误报，输出 `deadlock test semaphore 2 OK!`。
- 官方 checker（`make -C ci-user test CHAPTER=8`）：`Test passed: 25/25`。

## 二、关键设计与取舍

### 1. 为什么“等待图有环”不够

`ch8_deadlock_sem2` 里 tid1 持有 sem2、等待 sem1，tid3 持有 sem1、等待 sem2，等待图上确实存在环。但 sem1 被 tid2、tid3 各持有一个，sem2 被 tid1、tid4 各持有一个；tid2 和 tid4 都没有后续请求，会先跑完并把资源还回来，环上的两个线程随后都能推进，所以它不会真正死锁。

因此判据不能是“等待图里有没有环”，而必须是“当前分配状态是否还存在一条让所有线程依次完成的安全序列”。安全序列的构造就是银行家算法的核心：

1. `work[i]` 初始化为信号量 i 的剩余量；
2. 找 `request == None`（没有在等待信号量）或 `request` 所需资源在 `work` 里还有余量的线程，视为它可以完成，把它持有的资源加回 `work`；
3. 重复第 2 步，直到没有线程能推进；全部线程都能完成则安全，否则为死锁。

### 2. 账本按 tid 索引

线程 id 在进程内唯一，且 `process.tasks` 本来就以 tid 为下标，所以账本统一用 `Vec` 按 tid 索引。线程创建时账本不会自动变长，因此在 `sys_semaphore_down` 里按当前 tid 懒扩容；信号量创建时则把已有线程的行补齐到新的信号量数量。

### 3. 检测必须在真正阻塞之前

如果先调用 `down`/`lock`，信号量计数已经减少、线程已经进入等待队列，再返回错误就需要把计数、队列、账本全部回滚，任何一处漏改都会留下不一致状态。现在的做法是：先判定，不安全就直接返回 `-0xdead`，锁和信号量的内部状态完全不动；安全才调用原语进入阻塞。

这也解释了 `mutex1` 的修复路径：模板里第二次 `lock` 会把自己挂进等待队列并永久阻塞，检测必须发生在这次 `lock` 之前。

### 4. mutex 与 semaphore 分开处理

mutex 是 0/1 资源，最常见的死锁是同一线程重复加锁，账本里记录 `mutex_owner` 后直接对比 tid 即可，判断代价最低。semaphore 有计数、可能被多个线程同时持有，必须走安全序列。当前 `deadlock_safe()` 只统计信号量请求，跨线程的 mutex 循环等待没有覆盖；这是本实现的边界，测例也不包含这种场景。

### 5. 账本与真实原语之间的同步窗口

`unlock`/`up` 会先把当前线程名下的持有量清零，再唤醒等待者；被唤醒的线程从 `down` 返回后才把资源记到自己名下。这中间账本会短暂地“高估”可用量。这个偏差的方向是乐观的：最多漏报死锁，不会误报，因此不影响 `sem2` 这种“不能误报”的测例。严格做法是在所有权转移的那一刻同步转移账本，或者把检测直接放进 `Mutex`/`Semaphore` 内部。

### 6. 只记录“当前这一次请求”

银行家算法理想上需要每个线程的“最大需求（max claim）”，但内核无法预知线程之后还会请求什么。这里只记录已经阻塞的那一次请求，并把 `request == None` 的线程视为可以完成。对本章测例成立，但它更接近“死锁检测”而不是一般意义上的“死锁避免”。

## 三、测例推演

### `ch8_deadlock_mutex1`

单线程先 `lock(mid)` 成功，账本记录 `owner = 当前 tid`；第二次 `lock(mid)` 时检测到 owner 就是自己，直接返回 `-0xdead`，不会把自己挂进等待队列。随后 `unlock` 清空 owner，测例打印 OK。

### `ch8_deadlock_sem1`

- tid1 持有 sem2，tid2 持有 sem1 + sem2，tid3 持有 sem3；
- 三个线程分别请求 sem1、sem3、sem2，三种资源的剩余量都是 0；
- 此时 `work` 全为 0，任何线程的请求都得不到满足，安全序列不存在；
- 最后一个发起请求的 tid2 判定 `safe = false`，返回 `-0xdead`，随后按测例逻辑释放自己持有的资源，其余线程被唤醒并退出。

### `ch8_deadlock_sem2`

- tid1 持有 sem2、请求 sem1；tid3 持有 sem1、请求 sem2；
- 但 tid2、tid4 没有请求，可先完成，分别归还 sem1 和 sem2；
- `work` 因此变为正数，tid1、tid3 依次可以完成；
- 安全序列存在，两次请求都返回安全，线程正常阻塞后被唤醒，零失败。

## 四、一个容易误判的坑：`sleep` 并不是系统调用

调试时 `ch8_deadlock_sem1` / `sem2` 的主线程打印完 `thread N running` 后就不再推进，看起来像死锁检测失效。实际原因是 `user_lib::sleep()`：

```rust
pub fn sleep(period_ms: usize) {
    let start = get_time();
    while get_time() < start + period_ms as isize {
        sys_yield();
    }
}
```

它是用户态忙等，依赖 `get_time` 系统调用。而 ch8 模板中 `sys_get_time` 仍然是返回 `-1` 的桩，导致 `get_time()` 恒为 -1，循环永不结束，主线程根本走不到 `semaphore_up`。把 ch4 的实现（`write_user_usize` 检查 `is_valid`、U 位、`writable`，并分别写 `sec` 与 `va + 8` 处的 `usec`）移植回来之后，两个 sem 测例立即通过。

## 五、局限与可改进之处

- **mutex 只检测自我重入**，跨线程的 mutex 循环等待没有纳入安全序列；
- **condvar** 没有参与账本，`condvar.wait` 期间的等待不会被检测；
- **线程异常退出**时不会自动清理账本；测例里线程都会显式释放资源，所以没有影响，但完整实现应在 `exit` 时回收其全部持有量；
- **请求只记录一次**，无法表达“线程之后还会请求更多资源”，因此属于检测而非通用的死锁避免；
- 所有权转移窗口内账本短暂偏乐观，见第二节第 5 点。
